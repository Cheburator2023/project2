<a id="header-1"></a>__Используемые термины__

__Термин__

__Определение__

__Схема__

__Контейнер\-шаблон анкеты\. Имеет уникальный идентификатор \(UUID\) и код вида schema\-XXXXX\. Содержит одну или несколько версий\.__

__Версия схемы__

__Конкретная редакция шаблона\. Имеет статусы: «Не опубликовано», «Опубликована»\. В рамках одной схемы только одна версия может иметь признак «актуальная \(система\)»\.__

__JSON Schema__

__Декларативное описание структуры данных анкеты \(типы полей, обязательность, перечисления, дефолты\)\.__

__UI Schema__

__Декларативное описание правил отображения полей: ui:widget, ui:readonly, ui:placeholder, ui:options, ui:order, dictionaryCode\.__

__JsonLogic\-правило__

__Атомарная единица бизнес\-логики\. Имеет тип \(видимость / обязательность / вычисление / вычисление в строке массива / валидация / подсказка / триггер типовых задач\), целевое поле \(JSON Pointer\), условие и комментарий администратора\.__

__Этапы E2E__

__11 предопределённых этапов планирования ML\-инициативы \(Постановка задачи, Поиск данных, Построение витрины, Разработка MVP, Разработка модели и др\.\)\. Закодированы в движке расчёта\.__

__Стрим__

__Тип исполнителя/направления \(модельный, источниковый, платформенный\)\.__

__Триггер типовых задач__

__Тип JsonLogic\-правила, активирующий добавление типовой работы \(PILOT\_SUPPORT, IND\_SOURCE\_TASKS и др\.\) в расчёт при выполнении условия\.__

<a id="header-5"></a>__3\. Предусловия__

• Пользователь аутентифицирован в системе SUMСМАРТ\_АНКЕТА\.

• У пользователя есть права на администрирование схем \(доступ к пункту меню «Администрирование → Схемы»\)\.

• Бэкенд\-сервис /calculate доступен \(требуется для проверки в режиме «Превью»\)\.

<a id="header-6"></a>__4\. Триггер__

Появилась необходимость в новой версии шаблона анкеты — например, при изменении методологии расчёта E2E, добавлении новых полей, корректировке справочников или появлении нового типа ML\-инициативы\.

<a id="header-7"></a>__5\. Постусловия__

<a id="header-8"></a>__Гарантии успеха__

• Создана новая версия схемы со статусом «Опубликована»\.

• Новая версия имеет признак «Актуальная \(система\) №1»\.

• Предыдущая актуальная версия \(если была\) автоматически потеряла этот признак, но осталась в системе для обратной совместимости с уже созданными анкетами\.

• Модули «Реестр анкет» и «Создание анкеты» используют новую версию для всех новых анкет\.

<a id="header-9"></a>__Минимальные гарантии \(при неуспехе\)__

• Изменения, не подтверждённые кнопкой «Сохранить», не попадают в опубликованную версию\.

• Текущая актуальная версия остаётся неизменной до момента явной публикации новой\.

• Все промежуточные правки доступны во вкладке «Редактор JSON» для восстановления вручную\.

<a id="header-10"></a>__6\. Основной успешный сценарий__

1\. Пользователь открывает раздел «Администрирование → Схемы» и видит реестр схем с колонками: «Схема / версия», «Актуальная схема», «Идентификатор», «Код», «Описание», «Стрим», «№ версии», «Статус версии», «Опубликована», «Комментарий к версии», «Обновлено»\.

2\. Пользователь нажимает кнопку «Добавить схему» в правом верхнем углу\.

3\. Система создаёт новую схему\-контейнер и автоматически — её первую версию со статусом «Не опубликовано»\. Версия открывается в редакторе на вкладке «Конструктор» по умолчанию\.

4\. Пользователь формирует структуру анкеты: перетаскивает типы полей \(string, integer, number, boolean, object\) из палитры «Типы полей» \(левая колонка\) в рабочую область, организует поля в группы \(object\), задаёт иерархию через дерево схемы \(нижняя панель\)\.

5\. Для каждого поля пользователь кликом открывает панель «Свойства» \(правее рабочей области\) и заполняет: подпись \(title\), описание, тип JSON Schema, флаг «Обязательное», виджет UI Schema \(text / select / updown и т\. д\.\), справочник \(привязка к словарю\)\. Путь поля \(/meta/id и т\. п\.\) формируется автоматически\.

6\. Пользователь переключается на вкладку «Логика» и для каждого вычисляемого или условно\-отображаемого поля создаёт правило: нажимает «\+ Новое правило» \(или ⌘D — дублировать существующее\), выбирает тип правила \(видимость, обязательность, вычисление, вычисление в строке массива, валидация, подсказка, триггер типовых задач\), указывает целевое поле через JSON Pointer \(например, /detailInfo/parameters/algorithmCoeff\), задаёт условие в синтаксисе JsonLogic, заполняет комментарий администратора со ссылкой на функциональное требование \(например, «ФТ\-014: подсказка про источник веса коэффициента алгоритма»\)\.

7\. Система валидирует каждое правило «на лету» и показывает индикаторы: «✓ Правило корректно» / «⊘ ошибки / ⚠ предупреждения», а также текущее значение условия на тестовых данных \(«Сейчас: true/false»\)\.

8\. Пользователь переключается на вкладку «Граф связей» и проверяет карту зависимостей: счётчик правил/полей/связей \(например, «11 правил · 11 полей · 22 связи»\), отсутствие повисших узлов и циклов\. При необходимости кликом по иконке ↗ на узле переходит в редактор логики конкретного правила в отдельной вкладке\.

9\. Пользователь переключается на вкладку «Превью», заполняет тестовые значения в левой панели формы и сверяет результаты в правой панели «Калькуляция»: итоговую оценку \(базовую по стриму, оценку с поправкой на коэффициент сложности, отклонение в %\), таблицу «Подробный расчёт → Модельный стрим» с разбивкой по этапам E2E\.

10\. Пользователь нажимает кнопку «Сохранить» в правом верхнем углу\. Система сохраняет версию в статусе «Не опубликовано»\.

11\. Пользователь инициирует публикацию версии \(через действие в реестре или в карточке версии\)\.

12\. Система меняет статус версии на «Опубликована», устанавливает признак «Актуальная \(система\) №1», снимает этот признак с предыдущей актуальной версии \(если была\), фиксирует дату публикации \(поле «Опубликована»\), сохраняет комментарий к версии\.



<a id="header-11"></a>__7\. Альтернативные потоки__

<a id="header-12"></a>__A1\. Прямое редактирование JSON \(вместо шагов 4–6 основного потока\)__

13\. Пользователь переключается на вкладку «Редактор JSON»\.

14\. Видит две параллельные колонки кода с подсветкой синтаксиса: JSON Schema \(структура\) и UI Schema \(отображение\)\.

15\. Редактирует JSON напрямую — например, вставляет фрагмент из другой схемы, выполняет массовую замену путей, тонко настраивает ui:options, dictionaryCode, ui:order, перечисления \(enum\)\.

16\. Система валидирует JSON «на лету»; при ошибке отображает индикацию\.

17\. При возврате на вкладку «Конструктор» визуальное представление эквивалентно внесённым правкам\.

Возврат к основному потоку: шаг 6 \(настройка правил логики\)\.

<a id="header-13"></a>__A2\. Сброс к заводской схеме__

1\. На любом шаге работы с реестром пользователь нажимает кнопку «Сбросить к заводской схеме» в правом верхнем углу\.

2\. Система отображает диалог подтверждения с предупреждением о деструктивности действия \(*ожидается на основе общего паттерна UI; явно на скринах не показано*\)\.

3\. При подтверждении реестр приводится к эталонному состоянию\.

4\. UC завершается: дальнейшая работа над прерванной версией невозможна\.

<a id="header-14"></a>__A3\. Дублирование существующего правила \(на шаге 6\)__

1\. Вместо «\+ Новое правило» пользователь выделяет существующее правило в списке\.

2\. Нажимает горячую клавишу ⌘D или кнопку «Дублировать» в заголовке правила\.

3\. Система создаёт копию правила с временным именем\.

4\. Пользователь меняет целевое поле, условие и/или комментарий\.

Возврат к основному потоку: шаг 7 \(валидация правила\)\.

<a id="header-15"></a>__A4\. Правило не срабатывает на тестовых данных \(на шаге 7\)__

1\. После сохранения условия правило получает бейдж «Сейчас: false»\.

2\. Пользователь либо корректирует условие в редакторе логики, либо переходит на вкладку «Превью» и меняет тестовые ответы так, чтобы проверить срабатывание\.

Возврат к основному потоку: шаг 8 \(граф связей\) после получения «Сейчас: true»\.

<a id="header-16"></a>__A5\. Обнаружены ошибки в правиле \(на шаге 8\)__

1\. В списке правил у узла видны индикаторы __⊘ N__ \(ошибки\) и/или __⚠ M__ \(предупреждения\)\.

2\. Пользователь кликает по правилу, читает диагностические сообщения\.

3\. Исправляет: меняет целевое поле, условие, тип правила\.

4\. Бейдж сменяется на «✓ Правило корректно»\.

Возврат к основному потоку: шаг 8 \(повторная проверка графа\)\.

<a id="header-17"></a>__A6\. Отказ от изменений без сохранения__

1\. На любом шаге до шага 10 пользователь уходит со страницы без нажатия «Сохранить» — закрывает вкладку, переходит в другой раздел\.

2\. Система __не сохраняет__ изменения\. Версия остаётся в исходном состоянии \(либо удаляется, если была создана в этой сессии — *уточнение требуется*\)\.

3\. Актуальная опубликованная версия не затрагивается\.

UC завершается без достижения цели\.

<a id="header-18"></a>__A7\. Создание новой версии для существующей опубликованной схемы__

1\. Вместо шага 2 пользователь раскрывает строку существующей схемы в реестре и инициирует создание новой версии\.

2\. Система создаёт «Версию N\+1» относительно текущей актуальной, копируя её содержимое как стартовую точку\.

3\. Новая версия имеет статус «Не опубликовано»\.

4\. Старая версия продолжает обслуживать существующие анкеты до момента публикации новой\.

Возврат к основному потоку: шаг 4 \(редактирование структуры\)\.

<a id="header-19"></a>__A8\. Сбой бэкенда /calculate \(на шаге 9\)__

1\. При переключении на «Превью» правая панель «Калькуляция» не отображает значения / показывает ошибку\.

2\. Пользователь не может сверить корректность расчёта\.

3\. Рекомендуемое поведение: __не публиковать версию__ до восстановления бэкенда; обратиться в техподдержку\.

<a id="header-20"></a>__8\. Особые требования__

• __Версионность\. __Публикация новой версии не должна ломать ранее заполненные анкеты\. Старые анкеты продолжают рендериться по той версии схемы, по которой были созданы\.

• __Трассируемость\. __Каждое JsonLogic\-правило обязано иметь заполненный комментарий администратора со ссылкой на функциональное требование \(ФТ\-XXX\)\. Рекомендуется ввести валидатор перед публикацией\.

• __Изоляция движков\. __Поля summary\.baseScoreStream, summary\.scoreWithComplexityCoeff, summary\.deviationFromBaseline, detailedCalculation, platformStreams считаются хардкод\-движком E2E v1 и не должны переопределяться через JsonLogic\. UI должен предотвращать создание computed\-правил на эти пути\.

• __Производительность\. __Граф связей пересобирается по запросу \(кнопка «Пересобрать раскладку»\), а не в реальном времени, для схем с большим числом правил \(> 50\)\.

• __Горячие клавиши\. __Во вкладке «Логика» поддерживаются: N \(новое правило\), ⌘D \(дублировать\), Del \(удалить\), ⌘K \(поиск\)\.

<a id="header-21"></a>__9\. Критерии приёмки__

Сценарий считается реализованным корректно, если выполняются все нижеперечисленные критерии\.

__№__

__Критерий приёмки__

__Способ проверки__

__AC\-1\.1__

__Кнопка «Добавить схему» создаёт новую схему\-контейнер и одну версию со статусом «Не опубликовано»\.__

__Открыть реестр → нажать «Добавить схему» → убедиться в появлении новой строки и автоматическом открытии редактора\.__

__AC\-1\.2__

__В реестре отображается иерархия: схема → версии\. У каждой версии видны собственные UUID, статус, дата публикации, комментарий\.__

__Раскрыть строку схемы в реестре, проверить отображение дочерних версий\.__

__AC\-1\.3__

__Признак «Актуальная \(система\) №1» в каждый момент времени имеет ровно одна версия каждой схемы\.__

__Опубликовать вторую версию существующей схемы → проверить, что у первой версии признак снят, у второй — установлен\.__

__AC\-1\.4__

__Все пять вкладок редактора \(«Конструктор», «Редактор JSON», «Логика», «Превью», «Граф связей»\) отображают одну и ту же сущность согласованно\.__

__Изменить поле в Конструкторе → проверить отражение в JSON, Логике \(если затронуто правило\), Превью, Графе связей\.__

__AC\-1\.5__

__Изменения в JSON\-редакторе валидируются «на лету»; при синтаксической ошибке отображается индикатор и блокируется сохранение\.__

__Внести синтаксическую ошибку в JSON Schema → убедиться в подсветке и недоступности «Сохранить»\.__

__AC\-1\.6__

__Каждое JsonLogic\-правило имеет бейдж текущего состояния \(«Сейчас: true/false»\) и валидности \(«✓ Правило корректно» / «⊘ N ⚠ M»\)\.__

__Создать правило с условием, заведомо истинным/ложным на тестовых данных → проверить бейджи\.__

__AC\-1\.7__

__Граф связей корректно отображает счётчики \(правил, полей, связей\) и типы связей \(«зависимость», «результат», «вход и выход»\)\.__

__Создать правило типа «Вычисление» → убедиться, что в графе появилась стрелка от поля\-источника к правилу и от правила к полю\-результату\.__

__AC\-1\.8__

__Превью корректно отрабатывает скрытие неактивных этапов E2E \(отображает их серым с прочерками вместо значений\)\.__

__Заполнить анкету так, чтобы выбранный каскад не требовал AML → проверить, что строка «AML разработка» в подробном расчёте отображается серым с «—»\.__

__AC\-1\.9__

__Кнопка «Сохранить» сохраняет правки в статусе «Не опубликовано», не затрагивая текущую актуальную версию\.__

__Внести изменения → «Сохранить» → проверить, что в реестре актуальная версия не изменилась, а новая видна как «Не опубликовано»\.__

__AC\-1\.10__

__Публикация версии меняет её статус на «Опубликована» и устанавливает признак актуальности с фиксацией даты/времени\.__

__Опубликовать версию → проверить в реестре: статус «Опубликована», бейдж «Актуальная \(система\) №1», дата в колонке «Опубликована»\.__

__AC\-1\.11__

__Уход со страницы без сохранения не приводит к потере данных опубликованной версии\.__

__Внести изменения → закрыть вкладку браузера → открыть схему заново → актуальная опубликованная версия не изменилась\.__

__AC\-1\.12__

__Кнопка «Сбросить к заводской схеме» требует явного подтверждения и недоступна для рядовых пользователей без прав администратора\.__

__Проверить наличие диалога подтверждения; протестировать с учётной записью без прав администратора\.__



<a id="header-22"></a>__10\. Связанные UC и зависимости__

• UC\-2\. Аудит существующей схемы — может выполняться параллельно/после UC\-1 другим актором\.

• UC\-\* \(не входит в текущую спецификацию\)\. Заполнение анкеты конечным пользователем через модуль «Создание анкеты v1/v2» — потребитель результата UC\-1\.

• UC\-\* \(не входит\)\. Управление словарями \(раздел «Словари»\) — поставщик значений для UI Schema полей с dictionaryCode\.

<a id="header-23"></a>__11\. Открытые вопросы__

• __ОВ\-1\.1\. __Явный механизм публикации версии на скринах не показан\. Требуется уточнить: это отдельная кнопка в редакторе, действие в контекстном меню версии в реестре или автоматический переход при «Сохранить» с галочкой «Опубликовать»?

• __ОВ\-1\.2\. __Что происходит с «Не опубликованной» версией, если её бросить \(см\. A6\)? Удаляется ли автоматически или остаётся как черновик? Если остаётся — сколько черновиков может быть на одну схему?

• __ОВ\-1\.3\. __Возможен ли rollback — публикация предыдущей версии в качестве актуальной без её редактирования?

• __ОВ\-1\.4\. __Каков SLA операции «Сбросить к заводской схеме»? Удаляются ли пользовательские схемы безвозвратно или архивируются?

• __ОВ\-1\.5\. __Параллельное редактирование: что произойдёт, если два администратора одновременно правят одну версию? Поддерживается ли блокировка, оптимистическая блокировка по revision, last\-write\-wins?

<a id="header-29"></a>__5\. Постусловия__

<a id="header-30"></a>__Гарантии успеха__

• Аудитор сформировал заключение о корректности схемы \(валидна / требует доработки / содержит дефекты\)\.

• Все обнаруженные дефекты задокументированы со ссылками на конкретные правила \(комментарий администратора, ФТ\-XXX\)\.

• Схема и её версии в системе не изменены\.

<a id="header-31"></a>__Минимальные гарантии__

• Чтение схемы не приводит к её изменению ни при каких действиях аудитора\.

• Действующая опубликованная версия продолжает обслуживать анкеты конечных пользователей\.

<a id="header-32"></a>__6\. Основной успешный сценарий__

1\. Аудитор открывает раздел «Администрирование → Схемы» и находит целевую схему через фильтры реестра \(по идентификатору, коду, описанию, стриму, статусу, дате\)\.

2\. Раскрывает строку схемы, выбирает версию для аудита \(актуальную или конкретную историческую\)\.

3\. Открывает версию в редакторе\. Видит заголовок с бейджем статуса \(например, «v1 · Опубликована · актуальная»\)\.

4\. На вкладке «Конструктор» получает обзор структуры: дерево полей слева в нижней панели, состав групп \(Meta, Модели, Итоговая оценка, Детальная информация, ML\-платформа, Объекты данных\) в центральной области\.

5\. Переключается на вкладку «Граф связей», нажимает «Пересобрать раскладку», изучает счётчики \(правил / полей / связей\) и визуальную карту: цепочки «поле\-источник → правило\-вычисление → поле\-результат», цветовые метки правил \(видимость, обязательность, вычисление и пр\.\), типы связей \(зависимость / результат / вход и выход\)\.

6\. Для каждого узла\-правила, вызывающего сомнения, кликает по иконке ↗ — система открывает редактор логики этого правила в отдельной вкладке\. Аудитор читает: тип правила, целевое поле \(JSON Pointer\), условие в JsonLogic, комментарий администратора \(ссылку на ФТ\-XXX\), бейджи валидности и текущего состояния\.

7\. Возвращается в исходную вкладку с графом, идентифицирует на нём правила с индикаторами ⊘ \(ошибки\) или ⚠ \(предупреждения\), фиксирует их\.

8\. Переключается на вкладку «Логика», использует фильтр\-чипы по типу правила \(Видимость, Обязательность, Вычисление, Валидация, Подсказка, Триггер типовых задач\) и поиск по полю/названию для систематической проверки всех правил по категориям\.

9\. Переключается на вкладку «Превью», прогоняет несколько тестовых сценариев заполнения анкеты \(типичные комбинации стримов, каскадов, источников данных\), сверяет результаты в правой панели «Калькуляция» с эталонными значениями: итоговую оценку, базовую по стриму \(СФЕРА\), оценку с поправкой на коэффициент сложности, отклонение в %, таблицу подробного расчёта по этапам E2E\.

10\. При необходимости открывает вкладку «Редактор JSON» для точечной диагностики структуры \(проверка ui:order, dictionaryCode, enum, default, readOnly\)\.

11\. Формирует итоговое заключение: фиксирует дефекты, рекомендации, ссылки на конкретные правила и поля\. Покидает редактор без нажатия «Сохранить» — схема остаётся в исходном состоянии\.



<a id="header-33"></a>__7\. Альтернативные потоки__

<a id="header-34"></a>__B1\. Случайное изменение в режиме аудита__

1\. Аудитор по ошибке вносит изменение в любой вкладке \(например, перетаскивает поле в конструкторе\)\.

2\. Система __не должна__ автоматически сохранять изменения\.

3\. Аудитор уходит со страницы без «Сохранить» — изменения отбрасываются, актуальная версия остаётся неизменной\.

<a id="header-35"></a>__B2\. Аудитор обнаружил критический дефект в актуальной версии__

1\. В ходе сценария \(например, на шаге 9 — несоответствие расчёта эталону\) выявлен критический дефект\.

2\. Аудитор оформляет инцидент во внешней системе \(трекер задач\) со ссылкой на конкретное правило и комментарий администратора \(ФТ\-XXX\)\.

3\. По итогам инцидента инициируется UC\-1 для создания исправленной версии\.

<a id="header-36"></a>__B3\. Граф связей не отображается / некорректная раскладка__

1\. На шаге 5 граф визуализирован плохо — узлы перекрываются, стрелки неразборчивы\.

2\. Аудитор нажимает «Пересобрать раскладку»\.

3\. Если проблема сохраняется, перетаскивает отдельные узлы вручную \(поддерживается согласно подсказке в легенде\)\.

<a id="header-37"></a>__B4\. Аудит исторической \(не актуальной\) версии__

1\. На шаге 2 аудитор выбирает не актуальную, а предыдущую версию схемы\.

2\. Редактор открывает её с бейджем «vN · Опубликована» \(без признака «актуальная»\)\.

3\. Все вкладки работают в режиме чтения, но изменения не должны быть возможны \(*поведение требует уточнения — на скринах исторические версии в редакторе не показаны*\)\.

<a id="header-38"></a>__B5\. Демонстрация заказчику__

1\. Аудит ведётся совместно с бизнес\-заказчиком в режиме демо\.

2\. Аудитор использует «Граф связей» как визуальный материал: показывает, как из ответов формируется итоговая оценка\.

3\. Параллельно открывает «Превью» с реальными значениями для иллюстрации\.



<a id="header-39"></a>__8\. Особые требования__

• __Read\-only защита\. __Должна существовать роль «Ревьюер» с правами только на чтение раздела «Администрирование → Схемы» — без возможности нажать «Сохранить» или «Опубликовать»\.

• __Полнота информации\. __Все правила обязаны иметь содержательный комментарий администратора\. Аудит правила без комментария затруднён, поэтому такие правила должны помечаться как «⚠ предупреждение»\.

• __Экспорт результатов\. __Желательна возможность экспорта схемы \(JSON Schema \+ UI Schema \+ список правил\) в файл для внешнего ревью\. На скринах явно не показано — кандидат на доработку\.

__Фильтр\-чипы по типу правила \(Видимость, Обязательность, Вычисление, Вычисление в строке массива, Валидация, Подсказка, Триггер типовых задач\) корректно фильтруют список\.__

__Применить чип «Подсказка» → в списке остаются только правила этого типа\.__

__AC\-2\.7__

__Поиск по полю/названию правила работает с подстрокой и нечувствителен к регистру\.__

__Ввести часть имени правила в верхнем/нижнем регистре → правило находится\.__

__AC\-2\.8__

__Превью корректно отображает форму и расчёт без сохранения тестовых данных в опубликованную версию\.__

__Заполнить тестовые поля в Превью → перезагрузить страницу → поля очищены, версия не изменена\.__

__AC\-2\.9__

__Расчёт в правой панели «Калькуляция» обновляется в ответ на изменение тестовых данных в Превью\.__

__Изменить значение поля в Превью → значения базовой/итоговой оценки и таблицы подробного расчёта пересчитываются\.__

__AC\-2\.10__

__Серое отображение неактивных этапов E2E \(с прочерками\) визуально отличимо от активных\.__

__В сценарии без AML и пилотирования проверить отображение строк «AML разработка», «05B\. Пилотирование модели» в таблице подробного расчёта\.__

__AC\-2\.11__

__Для каждого правила доступен комментарий администратора с ссылкой на функциональное требование\.__

__Открыть произвольное правило в редакторе логики → проверить наличие поля «Комментарий администратора»\.__

__AC\-2\.12__

__Пользователь с ролью только\-чтение не может нажать «Сохранить», «Опубликовать», «Сбросить к заводской схеме»\.__

__Войти под учётной записью «Ревьюер» → проверить, что кнопки задизейблены или скрыты\.__

<a id="header-46"></a>__3\. Перечень разделов схемы \(корневые группы\)__

• Meta — метаданные анкеты \(идентификатор, наименование, статус, версия\)\.

• Модели — характеристики ML\-моделей \(список моделей, тип каскада/ансамбля, тип рекалибровки\)\.

• Итоговая оценка — агрегированные результаты расчёта \(summary\.\*\)\.

• Детальная информация — параметры расчёта \(включая algorithmCoeff\)\.

• ML\-платформа — инфраструктурные характеристики\.

• Объекты данных — источники, приёмники, фильтры, процессы обработки данных, контроль моделей\.
