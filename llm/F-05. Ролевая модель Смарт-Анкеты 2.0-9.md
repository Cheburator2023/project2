**Оглавление**

**Цель:** Описать, как существующие роли сотрудников в СУМ (Системе Управления Моделями) будут работать в новом модуле Смарт-Анкета 2.0.

В системе СУМ уже выделены следующие группы пользователей (описание в [Ролевая модель СУМ, СУРМ, Смарт-анкета](https://sfera.inno.local/knowledge/pages?id=1806005) ).

По сравнению с V1, в V2 появляются функциональные блоки, требующие расширения ролевой модели: конструктор шаблонов анкет, управление справочниками, жизненный цикл версий схемы, процесс поблочного заполнения и согласования анкет, отдельное действие «Утверждение» для периодической фиксации среза анкеты.

## **1\. Структура анкеты и модель заполнения**

Понимание структуры анкеты необходимо для корректной трактовки прав доступа: большинство прав действует не на анкету целиком, а на отдельные её блоки в разрезе стримов.

### **1.1. Блочная структура**

Анкета - единый объект, состоящий из блоков. Над одной анкетой работают несколько стримов, каждый в своей части:

• Блок «Общая информация» - общий блок анкеты: общая информация и данные по архитектурному компоненту «Модельный сервис». Не принадлежит конкретному стриму-исполнителю.

• Блок «Детальная информация» - заполняется в разрезе архитектурных компонентов «Система-источник», «Объект/Витрина данных», «Процесс обработки данных», «Модель». Параметры заполняются разными стримами; формируется перечень типовых работ, отдельно указываются нетиповые работы.

• Блоки по стримам - у каждого стрима свой блок с локальными параметрами и перечнями типовых и нетиповых работ. Например, стрим «Контроль моделей» имеет свои локальные параметры, которые заполняет представитель этого стрима с соответствующей ролью.

### **1.2. Статусная модель**

Статусы ведутся на двух уровнях - блока и анкеты в целом:

**Статус блока:** создано → в работе → заполнено. Переход в «заполнено» выполняется ответственной за блок ролью (действие approve, см. ФТ-6).

**Статус анкеты:** черновик → завершено. Анкета переходит в «завершено», когда все её блоки имеют статус «заполнено». Дополнительный статус «утверждена» присваивается при фиксации среза (см. ФТ-9).

### **1.3. Жизненный цикл: заполнение → завершение → утверждение → новая версия**

Роль с правом создания заводит анкету. Стримы дозаполняют свои блоки в существующей анкете, каждый подтверждает завершение своего блока. Когда все блоки заполнены, анкета переходит в «завершено». Руководитель программ ДАДМ может заблокировать анкету, зафиксировав срез на отчётную дату. Для продолжения работы в следующем периоде создаётся новая версия анкеты путем копирования: данные из утверждённой версии переносятся в неё, представители стримов редактируют свои блоки уже в новой версии. Утверждённая версия остаётся неизменной как исторический срез.

## **2\. Фильтрация по стримам**

Фильтрация по стриму - сквозная: действует одновременно на уровне списка анкет и на уровне содержимого (блоков) анкеты. Точная степень ограничения зависит от роли.

### **2.1. Рядовые исполнители (DS, DE, ModelOps)**

Жёсткий фильтр: видят в реестре только анкеты, где участвует их стрим. Внутри такой анкеты - полная детализация всех доступных блоков, включая состав работ с оценками по своему стриму.

Анкеты, в которых их стрим не участвует, недоступны: не отображаются в списке и не открываются по прямой ссылке (HTTP 403).

### **2.2. Lead-роли и роли уровня ДАДМ (DS Lead, DE Lead, ModelOps Lead, Архитектор данных ML, Аналитик ДАДМ)**

Видят в реестре анкеты всех стримов и могут открыть любую карточку. В карточке анкеты не своего стрима им доступны общая информация и детальная информация (архитектурные компоненты «Система-источник», «Объект/Витрина данных», «Процесс обработки данных», «Модель» и их параметры) - по всем стримам одинаково.

Состав работ (типовые и нетиповые) с оценками виден только по своему стриму; по чужим стримам этот блок скрыт. Механика нужна для синхронизации работ между стримами (избежание двойной работы по пересекающимся задачам - геоданные, антифрод, скоринг), при этом состав работ и оценки в человеко-часах остаются приватными для каждого стрима.

### **2.3. Роли с фильтром по стриму без урезания детализации**

Бизнес-партнёр стрима и Аналитик качества данных видят в реестре и карточке только анкеты своего стрима, но внутри них - полную детализацию (без урезания оценок).

### **2.4. Роли без фильтрации**

Бизнес-партнёр (штабной), Прикладной администратор, Аудитор ИБ, Аудитор, Руководитель программ ДАДМ, Конфигуратор Смарт-Анкеты видят все анкеты всех стримов. Полнота детализации карточки для них - согласно матрице (Руководитель программ ДАДМ и Конфигуратор - полная, с оценками; прочие - согласно примечаниям).

### **2.5. Редактирование в разрезе блоков**

Право на редактирование действует только на блок своего стрима и только в анкете, где этот стрим участвует. Например, DE Lead редактирует блок DE в анкете своего стрима; блок DS он не редактирует, даже находясь в той же анкете. Блоки «Общая информация» и "Детальная информация"- общие, доступны для редактирования в пределах полномочий.

## **3\. Функциональные требования**

**ФТ-1: Управление доступом на основе ролей (RBAC)**

**Описание:** Система должна обеспечивать разграничение доступа к функциям просмотра, создания, редактирования блоков анкет, работы с конструктором шаблонов, управления справочниками, согласования, утверждения и аудита на основе разрешений, назначаемых пользователям в Keycloak. Решение о доступе принимается на основе пермишенов (realm roles), а не самих ролей (groups).

**Сценарий:** Backend при запросе от клиента проверяет наличие необходимого разрешения. При отсутствии - HTTP 403. Frontend дополнительно скрывает UI-элементы и блокирует переходы по защищённым маршрутам.

**ФТ-2: Просмотр списка анкет (реестр)**

**Описание:** Доступ к реестру и состав видимых анкет определяются фильтрацией по стриму. Рядовые исполнители видят только анкеты своего стрима; Lead-роли, роли ДАДМ, аудиторы, администраторы и Конфигуратор - все анкеты. Бизнес-заказчик доступа к реестру не имеет.

**Сценарий:** DS входит в систему, видит в реестре только анкеты своего стрима. DS Lead видит все анкеты системы.

**ФТ-3: Открытие карточки анкеты и видимость блоков**

**Описание:** Объём видимой в карточке информации определяется механиками §2.1-2.4. Общая и детальная информация (арх-компоненты и их параметры) доступны в объёме доступных пользователю анкет. Состав работ (типовые и нетиповые) с оценками виден только по своему стриму; по чужим стримам этот блок скрыт. Рядовые исполнители видят только анкеты своего стрима (жёсткий фильтр) и внутри - полную детализацию. Для Валидатора карточка открывается, но виден только блок общей информации.

**Сценарий:** DS Lead открывает анкету, где участвуют стримы DS и «Контроль моделей». Общую и детальную информацию видит по обоим стримам. Состав работ с оценками видит по блоку DS (свой стрим); по блоку «Контроль моделей» состав работ и оценки скрыты.

**ФТ-4: Создание анкеты**

**Описание:** Создавать и скопировать версию анкету могут роли с правом create по матрице: DS Lead, ModelOps Lead, Конфигуратор Смарт-Анкеты, Представитель стрима-не участника ЖЦМ. Создатель заводит анкету как объект; остальные стримы дозаполняют свои блоки в уже существующей анкете.

**Сценарий:** DS Lead создаёт новую анкету по модели своей команды, заполняет доступные ему блоки, сохраняет. Анкета сохраняется в статусе «черновик». Представитель стрима «Контроль моделей» позже открывает эту анкету и заполняет свой блок.

**ФТ-5: Редактирование и удаление блоков анкеты**

**Описание:** Право редактирования действует на блок своего стрима в анкете своего стрима (§3.5). Полный набор (create/edit/delete) имеют DS Lead, ModelOps Lead, Конфигуратор, Представитель стрима-не участника ЖЦМ. DE Lead и Архитектор данных ML имеют редактирование без создания и удаления. Аналитик качества (ДАДМ) редактирует только свой раздел (контроль моделей). Рядовые исполнители, аудиторы, Валидатор и роли-читатели прав на модификацию не имеют.

**Сценарий:** DE Lead открывает анкету своего стрима, добавляет нетиповую работу в блок своего стрима, сохраняет. Блок, заполненный DS из другого стрима, в той же анкете остаётся ему недоступен для редактирования. В случае ошибочного создания анкеты DS Lead может её удалить.

**ФТ-6: Подтверждение завершения заполнения блока (approve)**

**Описание:** Действие approve - подтверждение завершения заполнения блока: перевод статуса блока в «заполнено». Право имеют роли, ответственные за соответствующий блок: DS Lead, DE Lead, ModelOps Lead - по своему стриму; Архитектор данных ML - по всем стримам; Аналитик качества (ДАДМ) - по своему разделу (КМ); Конфигуратор - без ограничений. Роль Валидатор в этом действии НЕ участвует. Когда все блоки анкеты имеют статус «заполнено», анкета переходит в статус «завершено».

**Сценарий:** DS Lead заканчивает заполнение блока DS и нажимает «Завершить заполнение» по своему стриму - блок переходит в «заполнено». Если DS Lead этого не сделал, а данные по части DE готовы, DE Lead может нажать «Завершить заполнение» по своему блоку. После того как все блоки анкеты заполнены, анкета автоматически переходит в «завершено».

**ФТ-7: Конструктор шаблонов (для Архитектора данных ML)**

**Описание:** Пользователь с ролью «Архитектор данных ML» должен иметь возможность редактировать draft-версии шаблонов в визуальном конструкторе (структура блоков, параметры, логика), публиковать версии.

**Сценарий:** Архитектор открывает конструктор шаблонов, создаёт черновик новой версии схемы, редактирует состав блоков и правила логики. Сохраняет черновик, публикует версию. Активация - см. ФТ-8.

**ФТ-8: Управление справочниками и активация версии шаблона**

**Описание:** Архитектор данных ML управляет справочниками и параметрами через конфигуратор. Активация опубликованной версии шаблона как глобально текущей доступна Архитектору данных ML и Прикладному администратору; при проблемах Прикладной администратор выполняет откат.

**Сценарий:** Архитектор редактирует справочник «Маппинг департаментов на стримы», добавляет запись для нового департамента, сохраняет, затем активирует новую версию схемы. Новые анкеты создаются по новой схеме.

**ФТ-9: Утверждение / блокировка анкеты (действие hold, фиксация среза) - для Руководителя программ ДАДМ**

**Описание:** Действие «Утверждение / блокировка» (в матрице - hold) - периодическая операция фиксации среза анкеты, отличная от approve. Approve подтверждает заполнение отдельного блока; утверждение фиксирует состояние всей анкеты на отчётную дату и блокирует её от изменений. Право на утверждение принадлежит исключительно роли «Руководитель программ ДАДМ» и никакой другой роли не выдаётся. После утверждения анкета переходит в статус «утверждена» и становится неизменной. Для продолжения работы в следующем периоде создаётся новая версия анкеты (см. ФТ-10).

**Сценарий:** Руководитель программ ДАДМ открывает завершённую анкету, просматривает её с полной детализацией, включая все оценки, и нажимает «Утвердить». Система запрашивает подтверждение, переводит анкету в статус «утверждена», записывает действие в журнал аудита с полным снепшотом содержимого. Утверждённая версия сохраняется как исторический срез.

**ФТ-10: Создание новой версии утверждённой анкеты**

**Описание:** После утверждения (блокировки) анкеты работа продолжается в новой версии. Создание новой версии доступно ролям с правом create (DS Lead, ModelOps Lead, Конфигуратор, Представитель стрима-не участника ЖЦМ). При создании новой версии все данные из утверждённой версии переносятся в новую, которая открывается для редактирования блоков представителями стримов. Утверждённая версия остаётся неизменной.

**Сценарий:** В начале нового отчётного периода DS Lead создаёт новую версию ранее утверждённой анкеты. Все данные переносятся. Представитель стрима «Контроль моделей» открывает новую версию и обновляет свой блок актуальными данными периода. Далее цикл повторяется: заполнение блоков → завершение → утверждение.

**ФТ-11: Формирование отчётов и экспорт**

**Описание:** Большинство ролей выгружает анкеты в отчётной форме. Валидатор и Validator Lead выгружают только список. Прикладной администратор права на выгрузку не имеет (сознательное ограничение - чтобы информация не покидала подразделение). Stream-filtered роли экспортируют только по своим стримам.

**Сценарий:** Аналитик качества работы моделей ДАДМ выбирает несколько анкет, нажимает «Экспорт». Система формирует xlsx. Бэкенд проверяет разрешение на выгрузку (в V1 проверка была только на фронте - исправляется в V2).

**ФТ-12: Аудит действий**

**Описание:** Система ведёт журналы значимых действий: операций с шаблонами (создание, публикация, активация, откат, удаление) и операций с анкетами (создание, редактирование блока, завершение заполнения блока, завершение анкеты, утверждение, создание новой версии, экспорт). Доступ к журналам - у ролей Аудитор ИБ, Аудитор и Прикладной администратор.

**Сценарий:** Аудитор ИБ фильтрует журнал по операции «утверждение анкеты», видит, кто, когда и какую версию зафиксировал.

**ФТ-13: Скрытие недоступных UI-элементов**

**Описание:** Кнопки действий и пункты меню должны быть полностью скрыты при отсутствии разрешения. Не допускается показ кнопки всем с возвратом 403 только при клике.

**Сценарий:** Аудитор входит в систему. Отсутствуют «Создать анкету», «Конструктор шаблонов», «Справочники». Видны «Реестр» и «Журнал аудита». В карточке анкеты нет кнопок «Редактировать», «Завершить заполнение», «Утвердить».

## **5\. Рекомендации для разработчиков**

### **5.1. Проверка пробрасывания ролей из смежных систем**

Необходимо проверить в Keycloak настройку мапперов токена. При переходе из смежной системы (СУМ, СУРМ, Data Lineage) в Смарт-Анкету 2.0 роли должны пробрасываться корректно, без «склеивания» несовместимых прав. Сессия в каждой системе должна иметь чёткий контекст.

### **5.2. Логика отображения UI-элементов**

**6.2.1. RBAC.** Если у роли нет прав на действие, элемент **полностью скрыт**.

**6.2.2. Статус процесса.** Если права есть, но статус блока/анкеты не позволяет действие (редактирование заполненного блока, утверждение незавершённой анкеты, редактирование утверждённой анкеты), элемент **отображён, но неактивен**.

### **5.3. Блочная модель прав**

Права edit, delete и approve действуют не на анкету целиком, а на блок конкретного стрима. При проектировании API права проверяются на паре «пользователь × блок», а не «пользователь × анкета»:

• Редактирование блока разрешено, если стрим блока совпадает со стримом пользователя (для stream-ролей) и роль имеет право edit.

• Approve переводит статус конкретного блока в «заполнено»; агрегатный статус анкеты «завершено» вычисляется, когда все блоки заполнены.

• Блок «Общая информация» - общий; правила его редактирования требуют отдельной фиксации (ОВ-5).

### **5.4. Разделение approve и утверждения**

• Approve - подтверждение заполнения блока. Множество ролей, действует на уровне блока, может выполняться многократно (по каждому блоку).

• Утверждение (столбец матрицы hold) - фиксация среза всей анкеты с блокировкой. Только Руководитель программ ДАДМ, периодическая операция, приводит к неизменяемой версии.

### **5.5. Версионирование при утверждении**

Утверждение не размораживается: продолжение работы реализуется созданием новой версии анкеты с переносом данных (паттерн new-version). Утверждённая версия хранится неизменной как исторический срез. Роли с правом create инициируют новую версию.

### **5.6. Фильтрация по стримам**

• Фильтр по стриму применяется и к списку, и к содержимому карточки, и к отдельным блокам, включая GET одной анкеты (закрытие дефекта V1).

• Скрытие состава работ (типовые и нетиповые) с оценками по чужим стримам - фильтр на уровне сериализации карточки. Общая и детальная информация (арх-компоненты, параметры) отдаются по всем стримам; блок состава работ с оценками - только по стриму пользователя. Требуется конфигурируемая схема «видимость блока × роль × принадлежность блока к стриму».

### **5.7. Аудит**

• Логируются операции с шаблонами и анкетами, включая завершение блоков, завершение анкеты, утверждение, создание новой версии.

• Утверждение логируется с полным снепшотом содержимого анкеты (для будущего аудита срезов).

• Доступ к журналам - у Аудитора ИБ, Аудитора и Прикладного администратора.
