# V2 — открытые вопросы и неопределённости

Документ собран после чтения `MAIN.md`, `DIAGRAM.md`, `ADMIN_IDEAS.md` и наброска доменной диаграммы (архитектурные компоненты). Используется для фиксации того, без чего нельзя зафиксировать продуктовое поведение или контракты.

---

## Метамодель и конфигурация анкеты

1. **Точное соответствие «разделам» типов 1–2–3 и JSON Schema / UI Schema.** MAIN описывает разделы и группы (параметры / компоненты / задачи). Не ясно, как это отражается в одной общей JSON Schema (одна форма или несколько `Form`/`$ref`), как задаётся условное появление разделов типа 3 (только через `logic`/`if-then`, через отдельные «страницы», или через ветки схемы).

2. **Версионирование X.0 vs X.1.** В MAIN мажорность привязана к логике расчёта и структуре зависимостей; в техническом стеке v2 уже есть версии snapshot (`V2TemplateVersion`). Нужны правила: что считается миноркой на уровне API (поля только UI, активность словарных значений) и автоматически ли выставляется тип версии человеком или пайплайном.

3. **Связь «один стрим — одна конфигурация».** MAIN: изменение конфигурации одного стрима не трогает другие. Подтвердить модель ключей шаблона (`streamCode`, `template.code`), поведение клонирования и дефолтных черновиков при первом сохранении.

## Архитектурные компоненты и справочники

4. **Финальный перечень компонентов и параметров.** В первую итерацию явно «не входит» финальный состав; нужен минимальный целевой набор для пилота, чтобы описать умолчаний в конструкторе и seed словарей.

5. **Справочник параметров компонента (нормативный).** F-01: параметры каждого типа компонента из отдельного справочника. Нужен формат связки «тип компонента → список параметров → тип данных / словарь / обязательность» и нужно ли версионировать этот слой вместе с шаблоном или отдельно.

6. **Справочник типовых задач и ключ триггера.** Согласовать канонический ключ правила (`тип компонента + параметр + значение`) при мульти-instance компонентах (два источника в одной анкете): как в данных анкеты идентифицируются экземпляры полей для сопоставления со справочником.

## Расчёт и логика (F-05 / F-06)

7. **Универсальная мультипликативная модель (F-05).** Проработка «низкая»: не определены вес по умолчанию, округление, границы коэффициентов и что считается «задача» как третья группа в произведении. Нужна формула в символах и примеры граничных случаев (нули, отсутствие группы).

8. **Формат итога (типовые vs нетиповые).** Отмечено «согласовать»: одна сумма или разнесение по типам задачам / стримам.

9. **Нетиповые задачи.** Default для «включено в расчёт» (Q-03 из MAIN применим). Диапазон коэффициента: фиксированный список или свободный ввод.

## Конструктор, RJSF, json-logic

10. **Канон хранения правил.** В контракте уже есть `V2LogicRuleDto` (`kind`, `targetPath`, `dependencies`, `condition`). Нужно утвердить семантику: как правило видимости/обязательности мапится на изменение schema/ui-schema в рантайме (кастомные `templates` vs предобработка схемы на бэкенде).

11. **Семантика `dependencies[]` для графа и циклов.** Определить направление рёбер (от чего к чему идёт зависимость) и нужны ли правила при пустых `dependencies`. Сейчас на фронте возможна только эвристическая проверка до утверждения модели исполнения.

12. **Палитра кастомных виджетов v2.** Список поддерживаемых в v2 имен (`ui:widget`) и нужны ли они в превью конструктора наравне со «стоковыми».

13. **Валидация и маски.** Где задаются маски (`pattern`, кастомные виджеты, отдельные правила `validation` в logic) и как это согласуется с ошибками Ajv в RJSF.

14. **`react-json-logic` и данные формы.** Согласовать префикс переменных в rules (`{"var":"/path"}` vs `formData.foo`) и единый «контекст оценки» для превью и бэкенда.

## Процесс, безопасность, эксплуатация

15. **Роли и права.** Кто может создавать/публиковать версии шаблонов и откатывать (только методолог / админ приложения)?

16. **Размер и лимиты.** В контракте есть лимиты JSON и числа правил; нужно ли лимитировать глубину вложенности схемы и число полей для UX и производительности превью.

17. **Аудит и откаты.** Полный журнал содержимого версий или только метаданные; требование ПДн при хранении diff.

## Известные технические огрехи (надо выровнять с бэком)

18. **HTTP-маршрут rollback для версий.** Целевой путь вида `/v2/templates/:templateId/versions/rollback` (POST) должен быть согласован с реальной реализацией контроллера (избежать конфликтующего шаблона параметров).
