## 1. Метамодель и конфигурация (F-01, F-02)

- **Q-V2-01.** Один глобальный конфиг анкеты или один конфиг на «стрим»? В тексте F-01 упомянуто «изменение конфигурации одного стрима не затрагивает конфигурации других стримов» — это значит, что у каждого платформенного стрима отдельная схема, объединяемая в рантайме, или один корневой документ с подчинёнными секциями?

Ответ: По началу будет одна версия, но структура должна быть готова к разделению. стрим определяется через справочник 

- **Q-V2-02.** Где границы между «структурой формы» (JSON Schema + UI Schema) и «справочниками» (опции selects, типы компонентов, типы работ)? Справочники хранятся как отдельные таблицы, как часть JSON-схемы (`enum` + `enumNames`), или подгружаются ленивыми запросами по `$ref`-подобному механизму?

Ответ: Справочники хранятся как отдельные таблицы, подумай как лучше их редактировать в админке. в отдельном разделе ui например

- **Q-V2-03.** Перечень типов архитектурных компонентов и их параметров — это часть схемы или отдельный нормативный справочник, на который схема ссылается? От этого зависит, нужна ли отдельная сущность `ArchitectureComponentType` в БД.

Ответ: Отдельный нормативный справочник, на который схема ссылается

- **Q-V2-04.** Что считается «активным» элементом (`is_active = true`)? Это атрибут в JSON-схеме (через UI schema/конфиг), отдельная колонка в справочнике или признак на уровне версии?

Ответ: Это атрибут в JSON-схеме. нужно управлять через UI schema пропами disabled/readonly и тп

- **Q-V2-05.** Конфиг — это файл (как сейчас «правится вручную и подкладывается разработчиком») или запись в БД с самого начала? Если файл — где он лежит, как доставляется до прода (миграция, seed, отдельный сервис)?

Ответ: Запись в БД с самого начала. Файл лежит в папке config в репозитории. в идеале без миграций (jsonb с жесткой типизацией)

- **Q-V2-06.** Поддерживается ли несколько одновременно действующих схем (например, разные шаблоны под разные ИС) или всегда ровно одна актуальная?

Ответ: Всегда ровно одна актуальная. но можно создавать новые версии и откатываться к старым. и нужно предусмотреть под разные ИС (информационный сервис)

### 14.1 Новые сущности из макетов

- **N-01.** Сущность «**Модельный сервис**» — в `Анкета. Заполнено` после «Общей информации» появляется отдельная карточка-таблица с моделями (имя, статус «Загружен», набор индикаторов). В требованиях её нет — это отдельный архитектурный компонент или отдельная типовая сущность?



- **N-02.** «**Рассчёт общей неопределённости**» — отдельная модалка с полями `Сроки инициативы`, `Стоимость инициативы`, `Поправка на общую неопределённость` + большой блок «Группа рисков» (12 select). Это отдельный механизм поправки на общую трудоёмкость? Где его место в расчёте F-05/F-06?
- **N-03.** В разделе «Объекты данных» в одной группе сразу **две подсекции**: «Витрины-источники данных для обучения» и «Витрины применения моделей» — каждая со своей таблицей и своей кнопкой добавления. Значит, в метамодели одна «Группа элементов» может содержать **несколько подгрупп-таблиц**.
- **N-04.** В разделе «Процессы обработки данных» — поле-чекбокс «Сквозной артефакт решения (УАСП)» с подсказкой «Расчёт по УАСП выполняется в составе артефакта». То есть нужны not только числа и select-ы, а ещё и **boolean с подсказкой/tooltip**.
- **N-05.** «**Редактирование названия**» — отдельная модалка для редактирования метаинформации анкеты (`Код анкеты`, `Название анкеты`). Это атрибуты заполненной анкеты, не схемы.
- **N-06.** «**Список версий**» (`Версия 3 — Активная`, `Версия 2 — Архив`, `Версия 1 — Архив`) — это версии **заполненной анкеты пользователя**, не версии схемы. Не путать с админскими версиями шаблона (F-07).

### 14.2 Структура «Итоговая оценка»

Из всех макетов видна стабильная правая колонка:

- `Базовая оценка по стриму (СФЕРА)` — большое число (например, `452`)
- `Оценка с поправкой на коэффициент сложности` — итог (`74.7`)
- `Отклонение относительно базовой оценки по стриму (СФЕРА)` — процент (`-83.47%`, красным/зелёным)
- Кнопка `ЭКСПОРТ В ЭКСЕЛЬ`
- Таблица **«Подробный расчёт»** с колонками:
  - Наименование архитектурного компонента
  - Базовая оценка по стриму (СФЕРА)
  - Итоговая оценка по коэффициенту сложности
  - Отклонение относительно базовой оценки по стриму (СФЕРА) — %
- Иерархические задачи: `05. Разработка модели` → `05.1 AML-разработка`, `08. Адаптация и внедрение` → `08.1 AML-внедрение`

- **`DropdownWithNormativesWidget`** — Dropdown с автоподстановкой нормативов после выбора (Класс модели → 9 значений → нормативы КД/ТМ/...)

- **`UncertaintyCalculatorWidget`** — Модалка «Общая неопределённость» (упомянут в Q-ADM-26)

### 17.5 Скорректированный план действий

С учётом релизной модели, последовательность для админки:

1. **R0** — техдолг V1 (см. чек-лист `v2_analytycs.md` §«R0» — `R0-BE-1..9`, `R0-FE-1..2`) — параллельно с финализацией требований.
2. **R1** — v2 MVP, шаблоны через миграции/сид. Заложить в БД сущность `anketa_template` и `template_version` уже в R1, чтобы R2 не ломал данные.
3. **R2** — админка-конструктор поверх `anketa_template`. Это и есть `ADMIN_IDEAS.md`.

То есть **бэкенд-фундамент V2-шаблонов нужно класть уже в R1**, а UI-конструктор — в R2.

**Предложение по PR #1**: создать сущности `v2_anketa_template` + `v2_template_version` + типы в `api-contract` + REST endpoints для чтения активной версии (R1 пользуется ими) и админский CRUD (заглушка, наполняется в R2).
